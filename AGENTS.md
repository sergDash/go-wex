# go+wex — скелет веб-приложения

Этот файл — индекс для агентов. Он отвечает на три вопроса: что это за проект,
как его запустить и куда идти за правилами. Подробности лежат в `doc/`,
а не здесь.

## Что это

Образец приложения, в котором бэкенд написан на Go, а интерфейс — на wex
(реактивная библиотека поверх jQuery). Прикладные проекты, включая TNS,
приводятся к этой структуре. Репозиторий — единственная линия развития,
ветка `main`.

## Запуск и проверки

```
go run ./cmd/app                  # http://127.0.0.1:8080, встроенный фронтенд
go run ./cmd/app -web ./web       # фронтенд с диска, без пересборки Go
go build -o bin/app ./cmd/app
go vet ./...
go test ./...
```

Внешних Go-зависимостей нет. jQuery и wex лежат в `web/vendor/`; обращений
к CDN в проекте быть не должно.

## Карта каталогов

| Путь | Назначение |
|---|---|
| `cmd/app/` | точка входа: флаги и запуск сервера, без логики |
| `internal/httpapi/` | HTTP-маршруты и JSON, без доменных правил |
| `internal/<домен>/` | доменная логика приложения |
| `web/` | фронтенд и локальные библиотеки |
| `doc/coding/` | правила кода |
| `doc/game/` | механики конкретных игр |

## Правила, которые действуют всегда

1. Данные идут одним путём: сервер отдаёт JSON → `app.js` кладёт его в стейт →
   шаблон выводит стейт. Прямая правка DOM и `innerHTML` из логики запрещены.
2. `internal/httpapi` не содержит игровых и предметных правил: обработчик только
   разбирает запрос, вызывает доменный пакет и кодирует ответ.
3. Поля JSON и имена полей стейта совпадают. Меняя структуру ответа, правь
   `internal/httpapi` и `web/app.js` вместе.
4. Стили — через переменные темы. Цвета в разметке и JS не задаются.
5. Документация обновляется в той же правке, что и правило, которое она
   описывает. Устаревшая инструкция хуже отсутствующей.
