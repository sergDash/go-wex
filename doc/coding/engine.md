# Устройство движка

Движок — это набор механизмов и стандарт, по которому к нему подключаются модули.
Всё, что не является механизмом движка, живёт в модулях.

## Три понятия

- **Модуль** — пакет, который подключается к ядру и объявляет свои возможности:
  маршруты, пункты интерфейса, слушателей, подкоманды, работы. Регистрация
  маршрутов — одна из возможностей, а не определение модуля.
- **Внутренняя служба** — долгоживущая часть процесса с запуском и остановкой.
  Она владеет своими горутинами и обязана дождаться их при остановке.
- **Работа** — единица фоновой работы, которая может быть поставлена в очередь
  и пережить перезапуск.

Остальное — средства: очередь, разборщик, исполнитель, пул, семафор, мьютекс,
таймер, тикер, расписание, журнал, проекция. Они не образуют отдельных слоёв
и не называются своими словами.

## Словарь

| Термин | Значение | Не путать с |
|---|---|---|
| Модуль | пакет, подключаемый к ядру | не подкоманда и не процесс |
| Ядро | точка сборки и владелец жизненного цикла | не отдельный процесс |
| Внутренняя служба | долгоживущая часть процесса | не системная служба |
| Работа | единица фоновой работы | не горутина и не функция |
| Пауза | прекращение новой работы без остановки | не остановка и не отмена |
| Очередь | хранилище работ, переживающее перезапуск | не канал |
| Разборщик | забирает работы из очереди | не планировщик |
| Исполнитель | горутина, выполняющая работу | — |
| Пул | ограниченное число исполнителей | не очередь |
| Семафор | счётчик разрешений | не мьютекс |
| Мьютекс | взаимное исключение | не семафор |
| Таймер | одно срабатывание через промежуток | не тикер |
| Тикер | таймер, который не выключается после срабатывания | не таймер |
| Расписание | правило, какая работа допустима при текущем простое | не тикер и не cron |
| Событие | запись журнала | не повод поставить работу |
| Отложенное событие | срок, по которому ставится работа | не запись журнала |
| Проекция | данные для интерфейса из состояния | не событие |
| Подсказка | сигнал «проснись, есть работа» | не транспорт |
| Подкоманда | режим запуска того же бинарника: `app report` | не модуль и не бинарник |
| Дочерний процесс | отдельный запуск с изоляцией | не внутренняя служба |

## Стандарт модуля

```go
type Module interface {
    Name() string
    Register(Registry) error
}
```

Модуль только объявляет. Ядро запускает и останавливает службы, разбирает
аргументы запуска и закрывает всё при остановке. Сокет и цикл приёма живут
внутри внутренней службы модуля: модуль открывает порт в `Start` и закрывает
в `Stop`, а ядро отвечает за порядок и срок остановки. Глобальных переменных
модуль не заводит; зависимости приходят через реестр.

### Возможности реестра

| Возможность | Что объявляет модуль | Что делает ядро |
|---|---|---|
| HTTP | метод, путь, обработчик | монтирует в HTTP-службу |
| Интерфейс | пункт: идентификатор, заголовок, порядок, адрес | отдаёт список пунктов данными |
| Подкоманда | имя режима, обработчик | разбирает аргументы, вызывает |
| Работа | вид, класс, обработчик, предел попыток, задержка | ставит в очередь и разбирает |
| Событие | вид, период, класс, полезную нагрузку по сроку | ставит работу по сроку и сдвигает срок |
| Служба | конструктор: цикл, слушатель TCP или UDP, проекция | запускает и останавливает в общем порядке |

Модуль описывает, что должно происходить; ядро владеет порядком запуска и
остановки. Ресурсы — порты, файлы, горутины — живут в службах и закрываются
их `Stop`. Это и есть
стандарт совместимости: любая возможность добавляется одинаково и закрывается
одинаково.

Вид работы модуль объявляет через `Registry.Job`: имя вида, обработчик, предел
попыток и задержку. Постановка работы — уже не объявление, а вызов разборщика
из обработчика запроса, поэтому разборщик приходит в модуль зависимостью при
сборке. Рабочий пример обоих путей — `domains/tasks`; полный набор
возможностей — `domains/demo`: HTTP, работа, событие, слушатели TCP и UDP,
процесс и подкоманда в одном модуле.

Отложенное событие модуль объявляет через `Registry.Event`: вид совпадает
с видом работы, поэтому обработчик один, а срок лишь решает, когда его
запустить. Полезная нагрузка собирается по сроку, иначе обработчик не знал бы,
за какой момент он работает. Срок хранится в хранилище и переживает
перезапуск; подробности — в `engine/events/AGENTS.md`.

## Внутренние службы

Служба имеет две операции: запуск и остановка. Группа служб запускает их
в порядке списка, останавливает в обратном и ждёт завершения с общим сроком.
HTTP-сервер — внутренняя служба. Слушатель TCP или UDP — внутренняя служба
(`engine/listen`): открывает сокет в `Start`, закрывает в `Stop`, перехватывает
панику на каждом соединении. Разборщик очереди — внутренняя служба.
Управляемый дочерний процесс — тоже служба, если ему нужно перезапускаться.

В точке сборки разборщик стоит раньше HTTP. Запуск идёт по порядку, остановка
в обратном, поэтому сначала закрывается приём запросов, и ни один новый запрос
не поставит работу в очередь, которую вот-вот остановят. Затем разборщик
получает отмену и доигрывает срок, отпущенный на остановку.

Перехват паники стоит на границе службы: паника записывается в журнал, служба
помечается отказавшей, процесс продолжает работу. Без перехвата одна паника
в горутине завершает весь процесс.

Пауза — необязательная возможность службы: её объявляет `Pausable`, а группа
вызывает в обратном порядке запуска. Пауза прекращает брать новую работу, но
не освобождает порты и файлы: для этого есть `Stop`. Нужна она двум вещам —
снизить нагрузку, приостановив управляемый процесс, и разобрать состояние
при отладке. Текущая работа доигрывается: прерывает её только отмена
контекста.

## Время

Время приходит из часов (`engine/clock`), а не из `time.Now` по месту. Часы
отдают текущий момент и одно срабатывание через промежуток; повтор — снова
срабатывание. В проверках подставляются остановленные часы, поэтому проверки
не спят.

Расписание (`engine/schedule`) — чистая функция от последней активности
и текущего момента. Оно отвечает, какие классы работ допустимы сейчас, и не
хранит времени; пороги хранятся как данные: «после пяти минут — фон». Догон
пропущенного времени вызывает ту же функцию, поэтому пропущенное срабатывание
ничего не ломает.

Активность запросов считает `engine/activity`: счётчик активных запросов и
метка последней активности. Пока запрос активен, разборщик убирает фон из
набора классов; простой отсчитывается от последней активности.

## Хранилище

Хранилище — один файл JSON-записей с номером версии. Записи сгруппированы
по коллекциям: имя коллекции → ключ → JSON. Открытие доводит файл до версии,
известной коду: недостающие миграции применяются по одной, файл новее кода
даёт отказ. Каждое изменение целиком переписывает файл через временный
и переименование, поэтому сбой оставляет старую или новую версию, но не
половину.

Ограничения видны в самом устройстве: один писатель в одном процессе, полная
перезапись при каждом изменении, форма записи проверяется читателем, а не
хранилищем. Этого достаточно, пока данные невелики; табличное хранилище
с частичной записью появится под объём. Правила формы данных, миграций
и версии — в `../schemas/storage.md`. Первый потребитель хранилища — очередь
работ: она сохраняет состояние при каждом изменении.

## Очередь и работы

Очередь — таблица, а не канал: канал теряет работу при перезапуске и не даёт
посмотреть, что было. Сейчас у строки есть вид, класс, тело, статус, попытки,
срок следующей попытки, номер, время создания и время начала попытки. Время
создания ставится при постановке и не меняется; время начала — при захвате
и очищается при возврате в очередь. Поэтому по строке видно, ждёт работа или
выполняется, а прошлые попытки остаются в журнале работы.

Очередь поверх хранилища записывает состояние при каждом изменении —
постановке, захвате, повторе, отказе. При открытии работа, застигнутая
в `running`, возвращается в очередь: попытка уже посчитана, но результат
неизвестен, поэтому работа выполняется заново. Это поведение «хотя бы один
раз», а не «ровно один раз»; повторный запуск должен быть безопасен.

Разборщик забирает работу одной транзакцией: выбрать подходящую строку,
поставить «выполняется», записать время начала, увеличить попытку. Это захват.
Без него два разборщика возьмут одну строку, а после падения нельзя отличить
«не начинали» от «начали и не закончили». Успех — «готово»; ошибка — назад
в очередь с задержкой; после предела попыток — «отказ». Статус строки виден
снаружи через `Get`: клиент спрашивает его по номеру, не дожидаясь выполнения.
Список всех строк отдаётся через `List` в порядке номеров: по нему строится
таблица состояния, и порядок не зависит от того, как легли записи в карте.

Классов работы достаточно двух: интерактивный и фоновый. Класс задаётся при
постановке; пустой берётся из правила вида, а если и там пусто, работа
считается фоновой. При захвате интерактивная идёт раньше фоновой, внутри
класса — по сроку, при равенстве — по номеру. Числовой приоритет —
необязательное поле, а не основа логики. Пул ограничивает число одновременных
исполнителей и ничего не хранит. Подсказка будит разборщик раньше тикера и не
заменяет очередь.

Разборщик спрашивает разрешённые классы перед захватом. Пустой набор не берёт
ничего: это пауза по расписанию, отдельная от ручной паузы. Набор приходит
из расписания по простою; пока идёт запрос, фон из набора убирается. При
пустом списке правил разрешены оба класса, поэтому расписание не обязательно.

Горутина и канал не заменяют очередь, потому что решают другую задачу.
`go f()` даёт выполнение в процессе, но не оставляет записи: работу нельзя
перезапустить, увидеть снаружи, повторить с задержкой или отложить до срока.
Канал — хорошая подсказка «проснись, есть работа», но плохое хранилище: он
ничего не помнит, не переживает перезапуск и не показывает статус. Разборщик
нужен затем, чтобы решать, какая именно работа допустима сейчас, с какими
попытками и по какому сроку. Горутина выполняет одну работу; очередь решает,
какие работы вообще должны выполняться.

Очередь похожа на асинхронность только по внешнему виду. Асинхронность прячет
ожидание: задача, которой нужны данные, отдаёт управление, её кадр остаётся
в памяти, а событие возвращает выполнение в ту же точку. В очереди кадра нет:
пока работа ждёт срока, существует строка с телом, статусом и сроком, а не
приостановленная функция. Поэтому ожидание в очереди — это не `await`,
а запись в таблице; состояние между шагами хранится явно, потому что
локальные переменные обработчика после возврата из него исчезают.

Пауза разборщика проверяется до захвата, в `Step`. Поэтому работа, взятая до
паузы, доигрывается, а следующая не берётся. Возобновление отправляет
подсказку, и разборщик не ждёт очередного тикера. Пауза — это состояние
в памяти процесса: после перезапуска разборщик снова работает.

## Отложенные события

Событие — это срок, по которому ставится работа, а не отдельный способ
исполнения. Поэтому событие ничего не выполняет само: оно кладёт работу
в очередь, а когда её взять, решают разборщик и расписание простоя. Своей
паузы, своих повторов и своего журнала выполнения у события нет: всё это уже
есть у работы.

Состояние события — одна запись в хранилище: срок следующего срабатывания.
Отсчитывать срок от момента запуска нельзя, иначе фаза расписания терялась бы
при каждом перезапуске. Новый вид получает первый срок через период от
текущего момента, а не срабатывает сразу на старте.

Догон даёт одно срабатывание, сколько бы сроков ни прошло: пропущенные сроки
не разворачиваются в очередь, а следующий срок прыгает к первому будущему
с сохранением фазы. Обращение через трое суток к событию с суточным периодом
ставит одну работу, а не три.

Работа ставится раньше, чем записывается новый срок. Сбой постановки
оставляет срок прежним, и следующий проход пробует снова. У обратного порядка
цена — тихая потеря события при падении; у выбранного — повторная работа
в узком окне падения. Выбор и его цена записаны в `../capabilities/Недостатки.md`.

## Запрос и работа

HTTP-запрос идёт прямым путём, пока его работа помещается в один ответ.
Служба `httpapi` принимает соединение, находит маршрут по методу и пути,
вызывает `core.Handler` в горутине запроса и кодирует возвращённые данные
в конверт. Пока обработчик работает, клиент ждёт; очереди и разборщика в этом
пути нет. Так устроен `GET /api/health`: снимок состояния собирается сразу
и отдаётся в ответ.

Другой путь нужен, когда работа долгая или может быть повторена. Обработчик
только кладёт работу в очередь и отдаёт номер, а выполнение идёт в горутине
разборщика; статус клиент спрашивает отдельным запросом. Данные проходят тот
же путь, но между постановкой и выполнением стоит таблица: тело — JSON, вид
выбирает обработчик, номер — то, что видит клиент. Разборщик подключается
службой при сборке. Первый вид работ — `task.run` в модуле `tasks`: запрос
`POST /api/tasks` ставит задачу и сразу отвечает номером, `GET /api/tasks/{id}`
показывает `queued`, `running`, `done` или `failed`, а пара
`POST /api/tasks/pause` и `POST /api/tasks/resume` проверяет паузу. Эти
маршруты — пример, а не обязательный набор предметной области.

Выбор между путями определяется свойством работы, а не вкусом. Ответ, который
нужен сейчас — состояние сервера, список, одно поле, — идёт прямым путём.
Работа, которая может ждать, повторяться и переживать перезапуск — отчёт,
индексация, рассылка, — идёт через очередь.

Маршрутизация и разборщик — разные механизмы, хотя оба выбирают, кому передать
управление. `ServeMux` выбирает обработчик по методу и пути внутри соединения;
разборщик выбирает строку работы по виду и сроку и не видит ни запроса, ни
ответа. Поэтому модуль пользуется общей маршрутизацией для HTTP, а разборщик
подключает только тогда, когда работа должна пережить запрос и повториться.

## Журнал работы

Журнал работы (`engine/journal`) — для разбора того, как идёт выполнение:
события, отказы, которые не привели к падению, повторы, паники, время
операций. Один писатель, дописывание в конец, ротация по размеру, хранение
нескольких файлов. Запись — строка JSON с временем, источником, видом и
полями; файл переживает перезапуск и дополняется, а не начинается заново.

Журнал включается настройкой `journal`: путь, предел размера и число копий.
Без раздела журнал отключён, и движок пишет только в обычный журнал процесса.
Разборщик пишет `done`, `retry`, `fail` и `panic` с номером работы и
длительностью; HTTP-служба пишет `panic` со стеком.

Журнал работы нужен, чтобы находить сбои, которые не роняют процесс: медленный
ответ, частый повтор, тихо обрезанные данные. Это отладочный инструмент,
а не отчёт о падениях.

## Опыт падений

Падение — отдельный вид знания. После разбора в `doc/experience/` появляется
текст: что случилось, что разрушилось, что сохранилось, что изменить. Это не
служба и не потоковая запись, а накопленные разборы, которые читают перед
правкой хрупкого места.

Код при падении оставляет минимум: перехваченную панику со стеком в журнале
работы, код завершения дочернего процесса, отметку о непройденной работе.
Последствия разбирает человек или агент: автоматически «понять», что именно
разрушилось, нельзя.

## Границы перехвата

Паника не должна покидать свою границу: HTTP-обработчик, цикл службы, одна
работа, обработчик соединения. На каждой границе паника записывается и
превращается в отказ, а процесс продолжает работу. Сейчас закрыты две
границы: HTTP-обработчик отвечает конвертом с 500 и пишет панику со стеком,
а одна работа возвращается в очередь или получает отказ. Границы цикла службы
и обработчика соединения появятся вместе со слушателями и процессами.

## Запуск себя

Тяжёлая или рискованная работа может идти дочерним процессом того же бинарника.
Подкоманда — это зарегистрированный режим запуска того же бинарника: например,
`app report --since=2026-11-01`. Ядро разбирает первый аргумент до запуска
служб; подкоманда не поднимает HTTP, хранилище и журнал, а выполняет одну
работу и завершается с кодом. Успех — код 0, ошибка — 1, неизвестный режим —
код 2 со списком известных. Модуль `tasks` объявляет `task --text=...`;
результат печатается строкой с версией протокола.

Подкоманды хранятся в `process.Registry` и объявляются модулем через
`Registry.Command`. Управляемый дочерний процесс (`process.Service`)
запускается в отдельной группе, читает вывод строками и пишет его в журнал
работы. Остановка посылает мягкий сигнал всей группе, затем принудительный
через срок; перезапуск после остановки прекращается. Ноль в сроке перезапуска
означает, что отказ не повторяется, а отмечается событием `failed`; ядро
продолжает работу.

Отмена идёт через контекст; остановка ядра не оставляет осиротевших процессов.
Если работа отменяема и не держит много памяти, дочерний процесс не нужен:
достаточно горутины.

## Раскладка

```text
go-wex/
  go.mod
  engine/           движок
    app/            package main: сборка, аргументы, сигналы
    config/         настройки из config/httpapi.json
    core/           стандарт модуля, реестр, возможности
    service/        внутренние службы и группа
    jobs/           очередь, захват, повторы, разборщик
    events/         отложенные события: срок, догон, постановка работы
    store/          хранилище JSON-записей: версия, миграции, атомарная запись
    httpapi/        HTTP-служба, конверт, статика
    clock/          часы: текущий момент и одно срабатывание
    schedule/       расписание: какие классы допустимы при простое
    activity/       счётчик активных запросов и метка активности
    journal/        журнал работы: дописывание и ротация
    listen/         слушатели TCP и UDP
    process/        подкоманды и управляемые дочерние процессы
  config/           httpapi.json: настройки, хранилище, пороги простоя
  domains/          модули предметной области
  interface/        статика
  schemas/          JSON Schema: настройки, обмен, версия хранилища
  doc/
```

`engine/app/` — точка сборки и единственное место, где движок знает о
`domains/`. Остальные пакеты движка о предметной области не знают.

Настройки приложения лежат в `config/httpapi.json`: адрес HTTP-службы,
каталог интерфейса и путь к файлу хранилища. `main` их не придумывает, а
читает через `engine/config`; пустое обязательное поле и неизвестный ключ
считаются ошибкой.

Каталога `internal` нет: `engine` и так является границей движка, а его пакеты
не предназначены для чужих проектов. Компилятор это не проверяет — проверяет
правило и `AGENTS.md` в каждом каталоге. Если когда-нибудь понадобится жёсткая
запретительная мера, единственный способ в Go — каталог `internal`.

Каталога `cmd` нет: он нужен, когда бинарников несколько. Здесь бинарник один,
поэтому `engine/app/` с `package main`.

В каждом каталоге лежит `AGENTS.md`: назначение, что здесь можно, что нельзя,
карта содержимого. Агент читает его раньше кода и не угадывает.

## Чего не делать

- не заводить глобальные переменные и сеттеры вместо зависимостей;
- не связывать модули общей шиной событий: они обмениваются данными через
  хранилище и очередь;
- не загружать код динамически: расширение — пакет или дочерний процесс;
- не прятать правила в таймеры: правила живут в расписании, таймеры только
  будят;
- не переносить слова из чужого проекта: у каждого механизма здесь одно имя.
